## 為什麼不只靠模型自我檢查

Diamond Studio 的流程分成規劃、執行、綜合和審查四個階段。綜合階段由語言模型寫出戰術報告。模型很擅長寫通順的段落，但也可能引用不存在的證據、把數字抄錯，或在兩人出局時建議犧牲觸擊。

這類錯誤大多可以用程式明確判斷。規則檢查便宜、結果穩定，也容易說明為什麼不合格，所以我讓它先跑。

## 規則檢查哪些事

| 檢查 | 不合格的例子 |
| --- | --- |
| 章節完整 | 報告少了範本要求的某一節 |
| 證據引用 | 引用了不存在的 `[E##]`，或某項影片觀察沒有附上證據 |
| RE24 數字 | 報告裡的期望值和工具算出的結果對不上，或根本沒有成功的 RE24 計算卻寫了數字 |
| 戰術與賽況 | 建議盜一個已經有人的壘包，或在兩出局時建議犧牲觸擊 |
| 洩漏球種 | 提到投手可能洩漏球種，卻沒有用「疑似」，也沒寫分析了幾球、樣本不足 |
| 測速數據 | 出現 mph 或 rpm，但這段影片沒有使用者確認的 Statcast 數據 |
| 限制說明 | 證據顯示有拍攝角度等限制，限制段落卻沒寫出來 |

數字比對會抓出報告中的期望值，和工具輸出的結果比較，容許很小的誤差。

## 退回與上限

規則找出問題後，問題清單會交回綜合階段重寫，最多兩次。第二次仍不合格時，報告照樣輸出，但會在頂端列出審查未通過的項目。

我刻意不讓它無限重試。與其讓系統一直改到看起來通過，不如誠實告訴使用者哪裡還有問題。

## 心得

規則檢查不能判斷推論是否合理，例如「投手動作偏慢」和「建議盜壘」之間的連結。但它把能用程式驗證的部分先擋下來，讓模型負責真正需要判斷的地方。這個分工比單純要求模型「請自我檢查」可靠得多。
