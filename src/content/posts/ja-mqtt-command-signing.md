## なぜ署名が必要か

灌水ノードは MQTT で「ポンプ起動」「ファン停止」などのコマンドを受け取ります。対応するトピックに発行できれば機器を操作できる仕組みだと、ブローカーにアクセスできる人なら誰でも遠隔でポンプを動かせてしまいます。通信を暗号化していても、「このコマンドは本当に許可されたシステムが、たった今送ったものか」を確かめる必要があります。

## コマンドの形式

コマンドには次の項目が含まれます。

- `command_id`：16 進数 32 文字のランダムな ID
- `timestamp` と `expires_at`：送信時刻と有効期限
- `action`：ON、OFF、または安全トピックでの RESET_FAULT
- `signature`：署名

署名は、トピック、ID、送信時刻、有効期限、動作をつなげた文字列に対し、共有鍵で HMAC-SHA256 を計算したものです。トピックも含めることで、「ファン起動」のコマンドをポンプのトピックに流用されるのを防ぎます。

## 受信時に順番に確認すること

1. メッセージが 700 バイト以下で、JSON として正しいこと。
2. ノードの時計が同期済みであること。同期前はすべて拒否します。
3. 時刻が妥当であること。送信時刻が 10 秒以上未来でなく、有効期間が 30 秒以内で、まだ期限切れでないこと。
4. ID の形式が正しく、動作が許可リストにあること。
5. 署名を再計算して比較すること。比較は一定時間で 1 文字ずつ行い、応答時間から署名を推測されないようにします。
6. その ID がまだ使われていないこと。

すべて通ったときだけ実行し、その場合でもファームウェアの安全インターロックを通過する必要があります。

## 使用済みコマンドを覚えておく

リプレイ防止には、最近使った ID と有効期限を記録する 64 枠のキャッシュを使います。ESP32 の不揮発性メモリに保存するので、再起動しても消えません。

キャッシュが満杯で、どれもまだ期限切れでない場合、ノードは古い記録を追い出すのではなく**新しいコマンドを拒否します**。追い出すほうが便利ですが、有効期間内のコマンドを攻撃者が再送できる余地が生まれてしまうからです。

## 報告にも署名する

コマンドを処理したノードは、受け付けたかどうか、現在の状態、理由（「実行済み」「安全インターロックで拒否」など）を報告します。この報告にも署名を付けるため、サーバーは結果が本当にノードから届いたもので、誰かが偽造した「停止済み」ではないと確認できます。

## 限界

共有鍵は各ノードに安全に書き込む必要があり、漏えいした場合はすべて交換しなければなりません。時刻の確認はネットワーク時刻に依存するため、時計が同期していない間、ノードは推測で動くよりもすべてのコマンドを拒否します。
