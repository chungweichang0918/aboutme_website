## モデルの自己チェックだけに頼らない理由

Diamond Studio は、計画、実行、統合、審査の 4 段階で動きます。統合の段階では言語モデルが戦術レポートを書きます。モデルは読みやすい文章を書くのが得意ですが、存在しない証拠を引用したり、数値を写し間違えたり、二死で送りバントを勧めたりすることもあります。

こうした誤りの多くはプログラムで明確に判定できます。ルールによる検査は安く、結果が安定していて、不合格の理由も説明しやすいので、先に実行します。

## ルールで確認すること

| 検査 | 不合格の例 |
| --- | --- |
| 章の構成 | テンプレートで必要な章が欠けている |
| 証拠の引用 | 存在しない `[E##]` を引用している、または動画の観察に証拠が付いていない |
| RE24 の数値 | レポートの期待値がツールの計算結果と一致しない、または RE24 の計算が成功していないのに数値を書いている |
| 戦術と試合状況 | 走者がいる塁への盗塁や、二死での送りバントを勧めている |
| 球種の癖 | 投手の癖に触れているのに「疑い」と書かず、分析した球数やサンプル不足にも触れていない |
| 速度データ | ユーザーが確認した Statcast データがないのに mph や rpm が出てくる |
| 限界の記載 | 撮影角度などの制約が証拠に表れているのに、限界の章に書かれていない |

数値の検査では、レポート中の期待値を取り出してツールの出力と比べ、ごく小さな誤差だけを許容します。

## 差し戻しと上限

ルールが問題を見つけると、その一覧を統合の段階に戻して書き直させます。上限は 2 回です。2 回目でも不合格なら、レポートはそのまま出力しますが、冒頭に審査を通らなかった項目を一覧で示します。

あえて無制限には再試行させていません。見た目だけ合格するまで書き直し続けるより、どこにまだ問題があるかを正直にユーザーへ伝えるほうがよいと考えたからです。

## まとめ

ルールでは、「投球動作が遅い」から「盗塁を勧める」へのつながりのように、推論が妥当かどうかまでは判断できません。それでも、プログラムで検証できる部分を先に止めておけば、モデルは本当に判断が必要な部分に集中できます。モデルに「自分で確認してください」と頼むだけより、ずっと信頼できる分担です。
